State Plane / UTM → Latitude & Longitude, in Arcade

One Arcade expression that converts a feature's stored projected coordinates to latitude and longitude — in Calculate Field, in a popup, or as an attribute rule that keeps them current as features are edited.

EPSG codes 1,139
Agrees with Pro to 0.07 mm
Verified against arcpy 3.7
Licence MIT

Arcade cannot reproject

A calculation against a feature class stored in a projected coordinate system returns northing and easting, not latitude and longitude. The numbers come back plausible and wrong — the failure mode that survives review. The only way through is to inline the inverse projection maths, and that maths differs per projection. So this carries the parameters for every zone and picks the right ones from the feature's own WKID at run time.

The claim is parity, not accuracy

Versions of this have circulated for years, each written for a single State Plane zone or a single UTM zone with its constants typed in. The exercise here was whether one expression could cover all of them — pick the right parameters from the feature's own WKID, pass geographic data straight through untouched, run inside an attribute rule — and still return what ArcGIS itself returns. It does. Nothing here is more accurate than Calculate Geometry Attributes, and nothing is meant to be. The point is that you give up nothing by doing it in Arcade, where a geoprocessing tool cannot go.

Coverage is every US State Plane zone across seven NAD83 realizations, every UTM zone worldwide on WGS 84 and the NAD83 realizations, and the BLM foot zones. Feature classes already stored in degrees pass straight through, so one expression serves projected and geographic layers alike.

Use it

// paste the file in as an Arcade expression, then set the mode at the top
var MD = "LAT";   // latitude as a number   -> Calculate Field, DOUBLE field
var MD = "LON";   // longitude as a number  -> Calculate Field, DOUBLE field
var MD = "BOTH";  // "Lat: 37.4952, Lon: -89.09" -> popups and labels
var MD = "RULE";  // attribute-rule dictionary writing both fields at once

Target a Double field. Float is single precision, caps you near 0.2 m, and throws away everything the maths earns. The numeric modes return nine decimals; BOTH is display text and formats to six, about 0.1 m — change FMT if you want more.

Four things attribute rules need, none of them obvious

  • A GlobalID field on the feature class, or creation fails with ERROR 002710.
  • Triggering fields are an explicit list, not a switch. Leave it empty and every update fires the rule — aggressively enough that a Calculate Field setting the fields to null is undone by the same edit. Name the shape field and only geometry changes fire it, which is usually what you want. Inserts fire either way.
  • The list can name any field, including one ordinary attribute. That is a deliberate recalculation handle: null the two fields, make a spare attribute the trigger, edit it, and the lat/long fills in — the quickest proof the rule works, and a way to re-run it over chosen rows without touching geometry.
  • A one-off Calculate Field pass to seed rows that already exist. An immediate rule only ever fires on edits, and a batch rule — which can backfill — accepts no triggering events, so it cannot also maintain.

A feature with no geometry blocks the edit. In RULE mode an unconvertible feature returns an errorMessage, and that aborts the edit rather than writing null — so a load that inserts attributes before shapes wants the rule disabled until the geometry is in. The other modes just return null.

The same answer as Calculate Geometry

Everything here answers one question — does inlining the maths cost you anything? — and the answer is no. These are not accuracy figures. They are the evidence that the expression lands on the same answer ArcGIS does.

Asked for the source's own geographic system, this expression and Calculate Geometry Attributes agree to the last digit that tool reports — it writes 8 decimal places of a degree, this writes 9. Checked across Transverse Mercator, Lambert Conformal Conic, UTM and Hotine zones, the worst disagreement is one unit in Calculate Geometry's final digit.

Worst disagreement 0.071 mm real engine, all 1,139 codes
Runtime errors 0 every code, every output mode
Test points 55,811 headless, plus 28,475 in-engine
Live parcels checked 47,630 every one, within 0.068 mm

0.071 mm is the floor: a file geodatabase quantises coordinates at 0.0001 m, which displaces a point by up to 0.07 mm before the expression ever sees it. The disagreement never rises above the noise floor of where the data lives.

Parity is also why zone parameters are read from arcpy.SpatialReference rather than EPSG's published tables. The two registries disagree on some constants, and the stored coordinates were made with ArcGIS's — so building from EPSG's rounded values pulls the answer up to 1.0 mm away from the one ArcGIS would give, which is the only kind of error that counts here. Two things to know before you trust it

A polygon's centroid can fall outside the polygon

Arcade's Centroid() is the true area centroid, not a guaranteed-inside label point, and Arcade offers no equivalent of one. On a real 47,630-parcel county layer that affected 449 parcels (0.94%), and on one 27,840-vertex parcel wrapping a lake the centroid sat 4.7 km from the parcel. If the coordinate must land on the feature, an attribute rule cannot give you that.

The datum question dwarfs everything above

An inverse projection does not change datum. ArcGIS's default NAD83 → WGS 84 conversion shifts by exactly 0.000 m, so the output is EPSG:4326 under the standard definition. But apply an explicit transformation instead and the same coordinate moves by up to 1.5 m — four orders of magnitude above the 0.07 mm this page spends its time on.

This is not a quirk of doing it in Arcade — and "what ArcGIS does by default" is not one thing. On the same NAD83 / Texas Central point asked for WGS 84, projectAs with no transformation named returns the coordinate unchanged, while Calculate Geometry Attributes applies WGS_1984_(ITRF00)_To_NAD_1983 and lands 0.935 m away. Calculate Geometry chooses by the data's extent, so it is not consistent even within NAD83: for UTM 15N in Minnesota it picked the null transformation and moved nothing. This expression matches the untouched-datum behaviour. Say which WGS 84 you mean.

NAD27 is deliberately unsupported. Those codes need a NADCON grid shift of up to about 100 m on top of the inverse projection, so inverting alone would return coordinates that look right and are 100 m wrong. Carrying a grid shift was not attempted here — a scope decision, not a claim about what Arcade can be made to do — so those codes are rejected with a message rather than silently mishandled. The same reasoning excludes OSGB36, Tokyo Datum and others.

What actually costs time

Arcade rebuilds the literal data tables on every feature, so lookup-table entry count drives run time and file size does not. Collapsing the WKID table into 380 arithmetic runs is what buys both.

Verify it, or adapt it

The build and verification toolchain is in scripts/ — the arcpy reference generator, a Node harness that executes the Arcade text, an Arcade-specific linter, and a runner for the real engine.

python scripts/validate.py builds/arcade_latlong_condensed.txt      # vs arcpy
python scripts/lint.py builds/arcade_latlong_condensed.txt          # Arcade checks
python scripts/run_in_arcade.py builds/arcade_latlong_condensed.txt # real engine

# build for projections outside the shipped list
python scripts/build_expression.py --codes 25832,25833 --out etrs89_utm.txt

Transverse Mercator, Lambert Conformal Conic and Hotine Oblique Mercator are implemented, on any ellipsoid in any linear unit. Codes using another method are reported and refused rather than silently mishandled.

If you build one for your own country, please send it back

The US scope reflects where the author works and nothing more. ETRS89 and the national grids, GDA2020 and MGA, the SIRGAS realizations, JGD2011 — a contributed code list plus the validator output is the whole contribution, because the build is generated from it. Projection methods this does not implement yet (Krovák, Stereographic, Cassini) are inverses that slot in beside iTM under a new type number. Grid-shift datums such as NAD27 and OSGB36 are the honest open problem, and worth a conversation in the issues if you have an approach. Open an issue or a pull request →

Run the linter after any edit. Arcade identifiers are case-insensitive, so U and u are the same variable — a hazard invisible to a JavaScript harness, and one that produced a real bug in the Hotine routine while this was being written.

A culmination, not an invention

The approach — inline the inverse projection, because Arcade cannot reproject — was worked out on Esri Community over many years, by people posting zone-specific expressions, correcting each other's constants, and porting the older GeoNet SQL versions across. What is new here is scope: every zone in one expression, parameters chosen from the feature's own WKID, and the whole thing checked against ArcGIS rather than trusted. The maths underneath is theirs and Snyder's.
